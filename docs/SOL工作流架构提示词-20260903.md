## 一、工作流的六个阶段（需求定义）

```
①论文检索 ②领域知识构建 ③创新点挖掘 ④实验设计 ⑤代码编写与监测 ⑥论文结构设计与写作
```

每个阶段的硬性要求：

**① 论文检索**（主力 L3+L2）
- 输入：研究问题/关键词 → 输出：结构化文献表（题目/venue/年份/一页表路径/相关性分级）
- 必须复用已有 9 份一页表格式（`seconde-paper/work-20260902/onepagers/`），不另起炉灶
- 增量原则：本项目文献地图已排重到 2026-09，工作流做**月度增量扫描**（arXiv/会议官网），不是从零重建
- 引用一律带 URL + 本地 PDF 路径，**身份核验步骤必须保留**（此前踩过 arXiv 编号误配的坑）

**② 领域知识构建**（L3 抽取 + L2 整理 + L1 审定）
- 手册/源码笔记/平台事实（本项目已有 RCCL/DUSHMEM 手册文本、源码完成语义笔记）入 Dify 知识库
- 分块策略：按文档节；元数据带 [PAGE N]/章节号，检索答案必须回显出处（本项目证据分级文化）

**③ 创新点挖掘**（L1 主导，人审强制）
- 输入=文献地图+实验结论+海光协作发现 → 输出=候选创新点列表，每条附"邻居占位对照"（对照一页表，防止宣称已被占阵地）
- **红线内建**：不复制论文原图；负结果照录；跨基座只比模式不比绝对幅度（用户与海光的既定协议）

**④ 实验设计**（L1 起草 → `experimental-design` skill 关卡 → 人审）
- 预注册模板自动生成（预测条目+判定程序，仿海光 P17 §7：符号优先/带缘±10pt UNDETERMINED）
- 设计产物落 `seconde-paper/work-<日期>/`，含 sample size/随机化/重复层级说明

**⑤ 代码编写与监测**（L1/Sol 直接写；**执行归 ZCode**）
- 分工边界：工作流产出=设计文档/脚本草案/验收清单；机器执行（GPU 实验/git push/交流窗提交）经 ZCode 或用户明示授权
- 监测：ZCode 侧已有模式（setsid 长任务+状态文件+看门狗）——工作流可订阅状态文件变化做"完成通知→触发下一阶段"（这是 Dify 触发器/n8n 事件的用武之地，若 Dify 不便可用系统 cron + curl 调 Dify API）

**⑥ 论文结构设计与写作**（L1 骨架+核心节，L2 中文初稿/润色，L3 格式与引用整理）
- 素材映射表已存在（五节×实验对应），工作流维护"素材→章节"的可追溯链接
- `scientific-critical-thinking` skill 作为投稿前自审关卡（GRADE 式过一遍每个 claim 的证据强度）

## 二、模型路由与成本守门（必须内建）

1. 每个节点标注目标模型层；L3（200 额度）节点全部经过"批量必要性审查"——能用规则/脚本做的不要烧模型
2. TokenDance 用量看门狗：Dify 里建一个全局变量/外部脚本每日检查用量，>80% 额度告警到交流窗式的本地日志文件并降级路由到 L2
3. L1（你自己）只出现在：架构裁决、创新点判定、实验设计关卡、论文核心段落、冲突仲裁
4. 所有 L2/L3 产出标记"机器草稿"标签，L1 或人审后才可入 git

## 三、与现有体系的集成契约（不可违反）

1. **git 纪律不变**：写完即入库、日期标注、大文件 tar+SHA256 不进 git
2. **交流窗协议不变**：工作流可以"起草"交流窗条目，但提交前必须人审（格式：【N】+秒级时间戳+内容+问题，最新在最上）
3. **预注册纪律不变**：涉及海光对表的数字，先封存后实测
4. **机器安全**：Dify 容器与 GPU 实验隔离（不同 compose 网络）；API keys 放 .env 不入 git；Dify 端口只绑本机或加认证（这台机器有公网能力）
5. **备份**：Dify 的 DSL（工作流导出文件）纳入 git 版本管理——工作流本身就是科研产出
